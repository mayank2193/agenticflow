`.github/workflows/agentic-test-pipeline.yml` on `mayank2193/agenticflow` (branch `master`) implements a planner → authoring → execution flow as a generic, reusable workflow, currently **2 jobs**: `planner`, then `authoring-execution` (authoring and execution were originally separate jobs but were merged 2026-08-17 to drop duplicated checkout/setup-node/install-kane-cli/login steps and an artifact hop that only existed to carry authoring's local meta forward — execution's `testrun run` now runs directly after authoring in the same workspace, so that meta is already on disk).

- **Trigger:** `workflow_dispatch` (manual, Actions tab) and `workflow_call` (so other workflows/repos can call it with `uses: mayank2193/agenticflow/.github/workflows/agentic-test-pipeline.yml@master` + `secrets: inherit`).
- **Inputs:** `requirements_doc` (blank = auto-detects first `*.pdf`/`*.docx` in repo root; must be a repo-relative path, not a github.com URL), `generation_objective` (defaults to the standard positive/negative/edge prompt), `test_language` (`javascript`/`python`, controls the kane-cli export step), `max_tests_to_author` (number, default `0` = no cap — caps how many of the planner's generated tests get authored+run), `kane_project_id`/`kane_folder_id` (both optional strings, blank by default — passed to `kane-cli login --project-id`/`--folder-id` when set; blank leaves kane-cli to auto-select the account default, same as every prior successful run's plain `kane-cli login`).
- **Required secrets:** `KANE_USERNAME`, `KANE_ACCESS_KEY`, `LT_USERNAME`, `LT_ACCESS_KEY` — not yet added to the repo as of 2026-08-17, so early runs failed at the `kane-cli login` step until the user adds them.

**planner job** — `kane-cli generate <objective> --files <doc> --agent` (objective and `--save` cannot be combined in one call — CLI errors with "--save takes no objective; use --refine to add to a request"), then a separate `kane-cli generate --save --req <id> --agent` call, with the `request_id` parsed out of the first call's `generate_done` JSON line. Uploads `generated-tests` artifact (`*_test.md` files) and publishes a job summary. No Test Manager link is possible at this stage — a test case only gets a TMS testcase ID once it's authored/run in the next job (`generate`/`generate --save` never emit one — checked their event types directly in the bundle: only `generate_save_result` with `suite_dir`/`saved`/`fell_back` counts, no testcase_id).

**authoring-execution job** (single job, runs after planner):
1. Downloads `generated-tests`, selects which files to author (respects `max_tests_to_author` cap, writes `selected_tests.txt`).
2. **Authoring**: `kane-cli testmd run <file> --headless --agent --code-export --code-language <lang>` per selected test — one call both syncs the test to TMS *and* exports its automation code (`kane-cli testmd export` alone fails with "this test has not been synced to TMS" if called on an unrun test). `--headless` required: GitHub-hosted runners have no display server. Each call's output is `tee`'d to a temp file (not `if !` around a bare pipeline — `set -e` sees `tee`'s exit status via the pipeline default, real status read from `PIPESTATUS[0]` right after) so one failing test doesn't abort the batch — failures logged as `::warning::`, counted, not fatal. Uploads `automation-code` artifact. **Its `test_md_summary`/`test_md_done` JSON carries a real public `share_url` and `testcase_id` per test when upload succeeds** — captured into `authoring_links.tsv` (`grep -o '"share_url":"[^"]*"' | sed -E 's/.*:"(.*)"/\1/'`, extraction verified against real captured JSON before shipping) and published as a job-summary table with both that public link and a derived private one (same URL, everything from `/dashboard/share/` onward stripped — confirmed against kane-cli's own URL builder function `Qn(host,project,testcase) = ${host}/projects/${project}/test-cases/${testcase}` found in the installed bundle).
3. **Execution**: `kane-cli testrun run <file1> <file2> ... --headless --on-failure continue --name "..."` **once** over all selected tests — kane-cli's dedicated command for bundling M tests into one sealed LambdaTest Test Run/evidence pack (not a loop of individual sessions). Doesn't accept `--agent` (errors "unknown option") but auto-emits NDJSON on non-TTY anyway. Requires each member to already have local meta (`output-<stem>/.internal/meta.json`, written by step 2's `testmd run`) or it's skipped as `"missing_meta"` — satisfied automatically now that authoring ran earlier in the same job/workspace. Output captured to `testrun_output.ndjson` (not `set -e`'d away, so the summary step still runs on failure).
4. **Evidence + summary**: evidence pack located at `.testmuai/evidence/<execution_id>.evidence` (confirmed via a real run — project-local, **not** `$HOME/.testmuai/kaneai/sessions/...`), uploaded as `test-run-evidence` artifact. `jq`-parsed markdown (per-test status/duration table, totals, overall status) written to `$GITHUB_STEP_SUMMARY`.

**Does NOT execute the exported Playwright code directly** (`node test.js`/`python3 test.py`) for the execution stage — tried first (with `TESTMU_RUN_TARGET=cloud` + `LT_USERNAME`/`LT_ACCESS_KEY`/`TESTMU_SMART=1` to route to LambdaTest's cloud grid via CDP relay) but LambdaTest rejects the replay with `400 Bad Request: "Test case validation failed: bad request"` — confirmed both locally and in CI. Root cause: the exported file's `testmu.configure({ tcId, build, ... })` values are fixed at export time and tied to that authoring session; replaying them standalone isn't supported. kane-cli's own `testmd run`/`testrun run` work because they create a fresh session each call.

**Execution (testrun run) still has no hosted LambdaTest link, by design choice**: confirmed empirically (`--dry-run` and a real headless execution) that `testrun run`'s output has **no** `share_url`/build link field — only `evidence_id`. User was asked to choose given this conflict (2026-08-17) and picked keeping `testrun run`'s grouped execution with no clickable links over reverting to per-test `testmd run` or running both (2x browser sessions). **This is still true** — what changed later the same day is that authoring's *own* `testmd run` calls (step 2 above) were found to already carry real `share_url`s in their output (previously discarded, now captured and published), so the pipeline does show real Test Manager links, just from the authoring stage rather than execution.

**Accessibility / Network / SmartUI — investigated, not wired up**: user asked to enable these LambdaTest capabilities for the execution run. Checked `kane-cli --help`, `kane-cli config --help` (`set-network-ws`/`set-network-sse` exist but no accessibility/SmartUI equivalent), and grepped the installed `@testmuai/kane-cli` bundle directly: no `LT:Options` capability builder anywhere in kane-cli's own code — `testmd run`/`testrun run` don't expose these as flags or env vars at all. Those toggles exist only in the separate `@testmuai/playwright-bindings` package (the exported-code path already abandoned for the 400 error above). User chose "skip for now" (2026-08-17) rather than fake flags that would silently no-op. Re-check kane-cli's changelog/`--help` before assuming this is still true if picking it back up later.

**Why:** User iteratively built this out across one long session (2026-08-14 through 2026-08-17): made it generic/reusable, then debugged real CI failures one at a time (bad doc-path input, `--save`+objective conflict, un-synced export, missing `--headless`, missing then-discovered-broken `TESTMU_RUN_TARGET=cloud`, bundled execution into `testrun run`, added project/folder inputs + execution job summary, merged authoring+execution into one job to cut duplication, then finally added planner/authoring job summaries with the real Test Manager links discovered in authoring's output).

**How to apply:** For a new requirements doc in this repo, just add the PDF/DOCX and trigger the workflow (blank `requirements_doc` works if it's the only doc in the root). For a different repo wanting the same pipeline, point a caller workflow at this file with `workflow_call` rather than copy-pasting the YAML. If kane-cli's CLI behavior changes (flag names, sync requirements, testrun output fields), re-check against `kane-cli --help`/`kane-cli testmd run --help`/`kane-cli testrun run --help` before assuming the workflow is still correct — several fixes in this file came from empirically testing kane-cli's actual behavior rather than trusting its docs alone.
