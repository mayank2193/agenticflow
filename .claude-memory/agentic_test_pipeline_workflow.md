`.github/workflows/agentic-test-pipeline.yml` on `mayank2193/agenticflow` (branch `master`) implements the planner → authoring → execution flow as a generic, reusable workflow:

- **Trigger:** `workflow_dispatch` (manual, Actions tab) and `workflow_call` (so other workflows/repos can call it with `uses: mayank2193/agenticflow/.github/workflows/agentic-test-pipeline.yml@master` + `secrets: inherit`).
- **Inputs:** `requirements_doc` (blank = auto-detects first `*.pdf`/`*.docx` in repo root; must be a repo-relative path, not a github.com URL — the checkout already has the file locally), `generation_objective` (defaults to the standard positive/negative/edge prompt), `test_language` (`javascript` or `python`, controls the kane-cli export + execution step), `max_tests_to_author` (number, default `0` = no cap — caps how many of the planner's generated tests actually get authored), `kane_project_id`/`kane_folder_id` (both optional strings, blank by default — passed to `kane-cli login --project-id`/`--folder-id` in every job's login step when set; blank leaves kane-cli to auto-select the account default, same as every prior successful run's plain `kane-cli login`).
- **Required secrets:** `KANE_USERNAME`, `KANE_ACCESS_KEY`, `LT_USERNAME`, `LT_ACCESS_KEY` — not yet added to the repo as of 2026-08-17, so early runs failed at the `kane-cli login` step until the user adds them.
- **Stages:**
  - **planner** — `kane-cli generate <objective> --files <doc> --agent` (objective and `--save` cannot be combined in one call — CLI errors with "--save takes no objective; use --refine to add to a request"), then a separate `kane-cli generate --save --req <id> --agent` call, with the `request_id` parsed out of the first call's `generate_done` JSON line.
  - **authoring** — first selects which generated `*_test.md` files to author: lists all of them (sorted), and if `max_tests_to_author` is set (>0) and less than the total, slices the first N into `selected_tests.txt` — this is the customizable limit on "number of tests created in planner which will then be authored." Then runs `kane-cli testmd run <file> --headless --agent --code-export --code-language <lang>` per selected test. This single call both syncs the test to TMS *and* exports the automation code — `kane-cli testmd export` alone fails with "this test has not been synced to TMS — run kane-cli testmd run first" if called on a test that was only generated (never executed). `--headless` is required: GitHub-hosted `ubuntu-latest` runners have no display server, so non-headless Chrome fails with "Chrome exited during startup with code 1". `kane-cli testmd run` exits non-zero whenever the test's assertions/replay fail — but it still syncs and exports code regardless — so the per-test call is wrapped in `if ! kane-cli testmd run ...; then` (not bare, under `set -e`) so one failing test doesn't abort authoring for the rest of the batch; failures are logged as `::warning::` and counted, not treated as fatal.
  - **execution** — downloads a single `authored-state` artifact from authoring (all of `.testmuai/tests/**` including hidden `.internal/` dirs, plus `selected_tests.txt`), then runs `kane-cli testrun run <file1> <file2> ... --headless --on-failure continue --name "..."` **once** over all selected tests — this is kane-cli's dedicated command for bundling M tests into one sealed LambdaTest Test Run/evidence pack, not a loop of individual sessions. `testrun run` doesn't accept `--agent` (errors "unknown option"), but auto-emits NDJSON on a non-TTY anyway. It also requires each member to already have local meta (`output-<stem>/.internal/meta.json`, written by a prior `testmd run`) or that member is skipped as `"missing_meta"` — confirmed locally with `--dry-run` — which is why authoring now ships its *entire* local `.testmuai/tests` state forward instead of just the bare `*_test.md` files, and the upload step sets `include-hidden-files: true` (upload-artifact drops dotfiles like `.internal/` by default). **Does NOT execute the exported Playwright code directly** (`node test.js` / `python3 test.py`) — that was tried first (with `TESTMU_RUN_TARGET=cloud` + `LT_USERNAME`/`LT_ACCESS_KEY`/`TESTMU_SMART=1` to route to the LambdaTest cloud grid via CDP relay, which does avoid needing a local browser binary) but LambdaTest rejects the replay with `400 Bad Request: "Test case validation failed: bad request"` — confirmed independently both locally (`node test.js` run by hand) and in CI. Root cause: the exported file's `testmu.configure({ tcId, build, ... })` values are fixed at export time and tied to that authoring session; replaying them standalone isn't a supported flow. kane-cli's own `testmd run`/`testrun run` work because they create a fresh session each call instead of replaying stale IDs.
  - **Execution job summary + evidence artifact** — execution captures `kane-cli testrun run`'s NDJSON to `testrun_output.ndjson`, locates the evidence pack at `.testmuai/evidence/<execution_id>.evidence` (confirmed via a real run — **not** under `$HOME/.testmuai/kaneai/sessions/...` as testmd's per-test evidence path pattern would suggest; testrun's pack is project-local), uploads it as the `test-run-evidence` artifact, and writes a `jq`-parsed markdown table (per-test status/duration, totals, overall status) to `$GITHUB_STEP_SUMMARY`. Confirmed empirically (both `--dry-run` and a real headless execution) that `testrun run`'s output has **no** `share_url`/build link field anywhere — only `evidence_id`. Per-test `kane-cli testmd run` *does* emit a real public `share_url` (pattern: `.../test-cases/<testcase_id>/dashboard/share/<token>?...`), with a private equivalent derivable by dropping the `/share/<token>` segment. User was asked to choose given this conflict (2026-08-17) and picked keeping `testrun run`'s grouped execution with no clickable links over reverting to per-test `testmd run` or running both (2x browser sessions).
  - **Accessibility / Network / SmartUI (investigated, not wired up)** — user asked to enable LambdaTest's accessibility, network, and SmartUI capabilities for the execution run. Checked `kane-cli --help`, `kane-cli config --help` (`set-network-ws`/`set-network-sse` exist but no accessibility/SmartUI equivalent), and grepped the installed `@testmuai/kane-cli` bundle directly: there is no `LT:Options` capability builder anywhere in kane-cli's own code — `testmd run`/`testrun run` don't expose these as flags or env vars at all. Those three toggles (`ACCESSIBILITY` env var, `network` via `testmu.configure()`) exist only in the separate `@testmuai/playwright-bindings` package used by the exported-code path, which is the path already abandoned above for the 400 error. User chose "skip for now" (2026-08-17) rather than fake flags that would silently no-op, or revisit the broken exported-code path. Re-check kane-cli's changelog/`--help` before assuming this is still true if picking it back up later.

**Why:** User asked (2026-08-17) to make the pipeline reusable/generic for future requirements docs, not hardcoded to the Airbnb PRD, and then iteratively debugged real CI run failures with me (bad doc-path input, `--save`+objective conflict, un-synced export, missing `--headless`, missing `TESTMU_RUN_TARGET=cloud`, discovering that target itself doesn't actually work for standalone exported-code replay, then bundling execution into one `testrun run` call) until authoring and execution both ran reliably.

**How to apply:** For a new requirements doc in this repo, just add the PDF/DOCX and trigger the workflow (input can stay blank if it's the only doc in the root, or pass its path explicitly — repo-relative, not a URL). For a different repo wanting the same pipeline, point a caller workflow at this file with `workflow_call` rather than copy-pasting the YAML. If kane-cli's CLI behavior changes (flag names, sync requirements), re-check this against `kane-cli testmd run --help` / `kane-cli generate --help` before assuming the workflow is still correct. See [[testcase-generation-flow]] for the equivalent local (non-CI) process, and [[airbnb-search-routing-suite]] for the suite this pipeline was built against.
